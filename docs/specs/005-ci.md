# Spec 005 — Kontinuerlig integrasjon

Status: CI-oppsett er implementert og kontrollert lokalt. Første kjøring på GitHub må bekreftes
etter at workflowen og appkoden er pushet.

## Formål

Alle kodeendringer skal få automatiske kontroller før de tas i bruk. Vi bruker
GitHub Actions med to separate jobber, slik at feil er lette å finne.

## Oppførsel

- `.github/workflows/ci.yml` kjører ved push til `main`, pull requests mot `main`
  og manuell start fra Actions. En arbeidsgren testes når den har en pull request.
- **Frontend:** Node.js 22, `npm ci`, TypeScript/produksjonsbygg, og Playwright
  med Chromium på desktop og mobil mot det ferdige bygget.
- **Backend:** Python 3.13 og PostgreSQL 17.11, låste avhengigheter, Django-kontroll,
  kontroll av manglende migrasjoner, migrasjoner på tom database og alle backend-tester.
- Backend har en separat, midlertidig database og offentlige testverdier.
  `.env` lastes ikke, og ekte OAuth-nøkler eller brukerdata skal ikke brukes.
- Nettlesertestene bruker isolerte API-svar. Backend-testene bruker PostgreSQL
  og simulerte OAuth-svar. CI verifiserer ikke ekte Google-innlogging eller produksjonsdrift.
- Jobbene har bare lesetilgang til repositoryet. Actions er låst til konkrete
  commit-ID-er fra de offisielle repositoryene. Checkout beholder ikke Git-legitimasjon.
- Frontend har grense på 15 minutter, backend 10. Nye kjøringer avbryter eldre
  kjøringer for samme pull request eller gren. Ingen periodiske kjøringer.
- Playwright bruker to arbeidere i CI, avviser `test.only` og prøver feilede tester
  én gang til. Ved jobbfeil beholdes HTML-rapport og testspor i sju dager.
  Avhengighetscache brukes for npm og pip; bygget publiseres ikke som nettsted.

## Akseptansekriterier

1. Et rent checkout kan kjøre begge jobbene uten apphemmeligheter.
2. Feil i bygg, tester eller migrasjoner gjør den aktuelle jobben rød.
3. Backend kjører mot en ekte PostgreSQL-database, adskilt fra utviklerens data.
4. Nettlesertestene kjører begge eksisterende skjermstørrelser og gir rapport ved feil.
5. Nye funksjonsmodulers backend-tester oppdages uten å redigere en liste i workflowen.
6. Workflowens syntaks og testkommandoer kontrolleres lokalt. En vellykket kjøring
   på GitHub dokumenteres separat når tilgang og push er på plass.

## Avgrensning

CI publiserer ikke appen og endrer ikke servere, kostnadsinnstillinger eller
branch protection. Krav om grønne kontroller før fletting settes separat i
GitHubs branch-regler; en rød CI-status alene forhindrer ikke fletting.
Ingen betalte tillegg aktiveres. Fakturering og inkluderte kvoter følger kontoens
GitHub-plan og må kontrolleres før eventuell betalt bruk.

## Verifikasjon

- `actionlint` 1.7.12 godkjenner workflowen; action-referansene er kontrollert
  mot de offisielle repositoryene.
- TypeScript og produksjonsbygg består med Node.js 22.23.4.
- Alle 24 nettlesertester består med `CI=true`, to arbeidere og CI-rapportering.
- Django-kontroll, manglende-migrasjoner-kontroll og migrasjoner på tom database
  består. Alle 22 backend-tester oppdages og består med Python 3.13.5,
  PostgreSQL 17.11 og workflowens testinnstillinger, uten å laste `.env`.
- Den lokale CI-databasen brukte egen datakatalog og port 5433; appens database
  ble ikke brukt. GitHubs PostgreSQL-container og Ubuntu-runner er ikke kjørt her.
- Dokumentlenker og whitespace er kontrollert. Ingen appkode er endret i CI-oppgaven.
- Første kjøring på GitHub gjenstår. SSH-tilgang fra arbeidsmiljøet ble avvist
  med `Permission denied (publickey)`. Workflow og tilhørende appkode må pushes
  fra et miljø med tilgang; CI er ikke bekreftet aktiv på GitHub ennå.
